# Licensing audit

Status: practical audit, not legal advice. It records what is bundled, under
which terms, and what to change before a public release.

## Project code

| component | license | notes |
| --- | --- | --- |
| `etng-core`, `etng-cli`, `xtask` | MIT | see `LICENSE` |
| `etng-tags` code | MIT | package metadata: `MIT AND Artistic-1.0-Perl` because the crate embeds generated data |
| Rust dependencies | permissive | `kamadak-exif` (MIT), `quick-xml` (MIT/Apache-2.0), `rayon` (MIT/Apache-2.0), `memmap2` (MIT/Apache-2.0), `serde_json` (MIT/Apache-2.0), `chrono` (MIT/Apache-2.0), `md-5` (MIT/Apache-2.0), `glob` (MIT/Apache-2.0) |

## Bundled ExifTool data — the only non-MIT payload

`crates/etng-tags/data/listx.xml` (18 MB) and the derived
`tags.tsv` (4.3 MB) are generated by `exiftool -listx -f` 13.55. ExifTool's
README states:

> Copyright 2003-2026, Phil Harvey
> This is free software; you can redistribute it and/or modify it under the
> same terms as Perl itself (either the Perl Artistic License or GPL).

Arch Linux records the package as `Artistic-1.0-Perl OR GPL-3.0-or-later`;
Debian/upstream wording is "same terms as Perl" (`Artistic-1.0-Perl OR
GPL-1.0-or-later`). This project relies on the **Artistic-1.0-Perl** option
and ships its full text in `LICENSES/Artistic-1.0-Perl.txt`.

Practical obligations that are already met:

- copyright notice retained (`NOTICE`, generated-file headers);
- license text included;
- the data is redistributed as generated/transformed data, not as ExifTool
  source, and the transformation is described (`tags.tsv` columns);
- no ExifTool code or Perl modules are linked or copied.

Residual risk: the snapshot embeds translated tag descriptions, which are
creative text authored by ExifTool contributors. Treat the snapshot as
Artistic-licensed data, never relicense it as MIT. If a downstream user
prefers a pure-MIT tree, they can delete `crates/etng-tags/data/*.{xml,tsv}`
and regenerate with `cargo xtask update-tags && cargo xtask generate-tags`
against their own ExifTool.

Alternative considered: generate the tables at build time and never commit
them. Rejected for now because it breaks offline/reproducible builds and makes
the golden corpus non-deterministic across ExifTool versions.

## Test corpus

| files | license | distributed? |
| --- | --- | --- |
| `tests/corpus/synthetic/*` and `make_cr2.py` | project-owned, MIT | yes |
| `tests/corpus/real/*` from `nom-exif` testdata | MIT (repository license) | yes |
| `tests/corpus/real/Canon_40D*.jpg`, `Nikon_D70.jpg`, `Sony_HDR-HC3.jpg` from `ianare/exif-samples` | CC BY-SA 4.0 (user-contributed; repository archived) | **no** — untracked, listed in `.gitignore` |

The vendor JPEGs were removed from git because CC BY-SA 4.0 imposes
attribution and share-alike on the images (and arguably on derived metadata),
which conflicts with a plain MIT repository. They remain on the development
machine for parity runs; `tests/corpus/PROVENANCE.md` documents this.

## Before a public release

1. Keep `NOTICE` and `LICENSES/Artistic-1.0-Perl.txt` in the repository and in
   source/binary distributions.
2. Do not relicense `listx.xml`/`tags.tsv`; leave the `etng-tags` package
   license expression as `MIT AND Artistic-1.0-Perl`.
3. Re-check the `-listx` header version after every ExifTool upgrade and
   regenerate tables + snapshots in one commit.
4. If the corpus grows, add every new file's origin/license to
   `tests/corpus/PROVENANCE.md`; do not commit samples without an explicit
   license.
5. Legal review is still advisable before a commercial distribution.
