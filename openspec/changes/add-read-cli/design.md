# Design

## Context

Проект новый, кода нет: репозиторий `~/work/etng`, Rust 1.92, local exiftool 13.55 как эталон. Спецификации поведения — `specs/metadata-read`, `specs/json-output`, `specs/cli`, `specs/exiftool-fallback`; мотивация — `proposal.md`.

Ограничения, задающие архитектуру:

- Совместимость проверяется сравнением с выводом exiftool 13.55, поэтому версия эталона фиксируется константой и не «плывёт» вместе с системным exiftool.
- `exiftool -listx -f` на этой машине отдаёт 31 942 тега в 1 224 таблицах с группами (`g0`/`g1`), типом и таблицами печатных конверсий (`<values>`) — это готовый источник метаданных о тегах, а не то, что нужно писать руками.
- Команда должна работать на тысячах файлов: старт и пакетная скорость — главная причина существования проекта.
- Код и идентификаторы — английские, артефакты и документация — русские (правило проекта в `openspec/config.yaml`).

## Goals / Non-Goals

**Goals:**

- Архитектура, в которой добавление формата или вендора MakerNotes не трогает CLI и сериализатор.
- Детерминированный, потоковый JSON-вывод с ограниченной памятью при любом числе файлов.
- Совместимость с exiftool, измеримая автоматически (дифф-тесты на корпусе), а не «на глаз».
- Гибридный режим, который позволяет внедрять etng постепенно, не блокируясь на непокрытых форматах.

**Non-Goals:**

- Write-режим (правка EXIF/XMP) — отдельное изменение; в этой архитектуре только резервируется слой `TagWriter`.
- Видео/аудио контейнеры (MOV/MP4/MKV), `-csv`/`-X`/`-php`/`-html` форматы вывода, XMP-пакеты с записью.
- Python/WASM-биндинги и публикация в crates.io — после стабилизации API.
- Побитовая идентичность вывода на всех 31k тегах: контракт — совпадение структуры, полей, порядка и форматирования на целевом корпусе, расхождения документируются.

## Decisions

### D1. Cargo workspace из трёх крейтов

`etng-core` (модель тегов, парсеры, сериализатор — без CLI-зависимостей), `etng-cli` (бинарник `etng`, разбор аргументов, обход файлов, fallback-процессы), `etng-tags` (сгенерированные таблицы тегов, подключается как обычная зависимость).

Альтернатива — один крейт: быстрее стартовать, но библиотека для встраивания и кодогенерация таблиц начинают протекать в CLI-слой. Альтернатива — отдельный крейт на каждый формат: преждевременно, форматов шесть и они делят TIFF-ядро.

### D2. Упорядоченная модель тегов, а не словарь

Запись файла — `FileReport { source: PathBuf, system: SystemFields, tags: Vec<Tag>, warnings: Vec<Warning>, error: Option<FileError> }`, где `Tag { group: GroupId, id: u32, name: &'static str, value: Value }`. Порядок тегов задаётся порядком вставки, который определяется планом эмиссии формата и порядком таблиц из `-listx`. `HashMap` в модели запрещён: он даёт недетерминированный порядок и ломает требование стабильного вывода.

### D3. Слоистый разбор: свой контейнер + готовые декодеры блоков

Конвейер: sniff → container walker → block decoders → нормализация.

- Контейнеры: JPEG-сегменты (свой сканер + `img-parts` для границ маркеров), TIFF/IFD (свой обход IFD с лимитами глубины и счётчиков), ISO-BMFF для HEIC (свой минимальный box-walker), DNG/CR2/NEF — как TIFF-семейство.
- EXIF-блок: `kamadak-exif` для IFD/типов значений; собственный слой поверх него для групп, имён и print conversion.
- HEIC/RAW: `nom-exif` как второй backend там, где своего обхода не хватает; его результат приводится к общей модели.
- XMP: `quick-xml` + курируемая карта RDF-свойств (`dc:`, `xmp:`, `exif:`, `photoshop:`, `crs:`).
- IPTC IIM: собственный минимальный парсер (формат — последовательность dataset'ов, внешняя библиотека не нужна).
- GPS: из EXIF, с печатной конверсией координат в стиле exiftool.

Альтернатива «всё на `kamadak-exif`» — нет HEIC/RAW и MakerNotes-группировки; альтернатива «всё своё» — годы работы; альтернатива «`rexiv2`» — тянет C++ exiv2 и убивает статическую сборку.

### D4. Таблицы тегов генерируются из `exiftool -listx`

Снимок `exiftool -listx -f` (13.55) кладётся в `etng-tags/data/listx.xml`, `cargo xtask generate-tags` превращает его в компактные Rust-таблицы: `(group0, group1, tag_id, name, type, writable, values[])`. Сгенерированный файл коммитится — сборка остаётся офлайн и воспроизводимой; `build.rs` только сверяет хеш снимка.

Это закрывает сразу три задачи: имена тегов и групп, типы для нормализации, таблицы печатных конверсий. Альтернатива — переносить таблицы вручную по мере надобности: не масштабируется и порождает расхождения в именах.

### D5. Собственный потоковый JSON-писатель

Пишем JSON напрямую в `BufWriter<Stdout>`: порядок полей, форматирование чисел, отступы и запятые под нашим контролем, запись файла уходит в поток сразу после разбора. Экранирование строк — через `serde_json::to_writer` для одного значения, чтобы получить RFC 8259-корректный escaping без своей реализации.

Альтернатива — собрать `serde_json::Value` и сериализовать: теряется порядок ключей без `preserve_order`-хаков, и весь результат держится в памяти, что нарушает требование потоковости.

### D6. Параллелизм пакетами с упорядоченной эмиссией

Список файлов режется на батчи (по умолчанию 64 файла или бюджет 16 МБ оценённого объёма). Батч разбирается через `rayon::scope`, результаты складываются в `Vec` по индексам и пишутся в stdout строго по порядку; после батча память освобождается. `--threads N` конфигурирует пул rayon, `0` — ошибка использования.

Альтернатива — `par_iter().map(...).collect()` на весь список: память растёт линейно, нарушает требование. Альтернатива — unordered-канал: ломает порядок вывода.

### D7. Fallback как отдельный процесс без shell

`std::process::Command::new("exiftool")` с массивом аргументов (никакого `sh -c`), наличие exiftool определяется один раз за запуск и кешируется. Делегируется файл целиком, флаги зеркалятся (`-j`, `-G1`, `-n`, `-s`), ответ парсится `serde_json` и переводится в `FileReport`; частичные теги собственного разбора объединяются с делегатом с приоритетом собственных. Ошибка запуска/невалидный JSON делегата превращается в `FileError`, а не в панику.

### D8. Собственный разбор аргументов в стиле exiftool

exiftool-синтаксис — одиночный дефис и произвольные имена тегов (`-Make`, `-EXIF:Make`), что конфликтует с моделью коротких флагов `clap`. Пишем свой парсер: таблица известных флагов + распознавание `-TAG`/`-GROUP:TAG` по таблицам из D4, `--flag=value` для собственных длинных опций (`--fallback`, `--threads`). Неизвестный флаг без совпадения по тегам — ошибка использования (код 2).

### D9. Форматирование: таблицы конверсий + явные правила

Значение тега хранится типизированным; при сериализации применяется правило: `-n` → машинное значение; иначе — `<values>`-конверсия из таблиц, затем форматтеры дат (`YYYY:MM:DD HH:MM:SS±HH:MM`), размеров (`27 kB`), рациональных (`1/250`). Теги без правила выводятся как есть; каждое такое расхождение попадает в `docs/divergences.md` по результатам дифф-тестов.

### D10. Ошибки — данные, паника — инцидент

`catch_unwind` вокруг разбора файла превращает панику парсера в `FileError` с диагностикой: один битый файл не должен убивать пакет. Код возврата агрегируется по политике из `specs/cli`. Лимиты (глубина IFD, число тегов, размер строки) задаются константами и покрываются фаззингом.

### D11. Совместимость проверяется корпусом, а не глазами

Три уровня корпуса: (1) минимальные синтетические файлы на каждый формат/блок, (2) реальные файлы Canon/Nikon/Sony/Apple в JPEG/HEIC/TIFF/DNG/CR2/NEF, (3) враждебные и обрезанные файлы. Эталонные JSON-снимки генерируются `exiftool -j` в момент обновления корпуса и коммитятся. Компаратор нормализует заведомо изменчивые поля (`FileAccessDate`, `FileInodeChangeDate`) и версию, затем сравнивает структуру, порядок и значения; отчёт — список расхождений по тегам.

Бенчмарки: `hyperfine` для старта (`-ver`, один файл), собственный harness для пакета 10k файлов против `exiftool -j` (время, RSS через `getrusage`/`/usr/bin/time -v`).

### D12. API для встраивания сразу, биндинги потом

`etng-core` публикует `read_file(path, &ReadOptions) -> FileReport` и `read_paths` с колбэком эмиссии. CLI — тонкая оболочка над этим API. Это даёт Rust-библиотеку бесплатно и оставляет место для Python/WASM в отдельном изменении.

## Risks / Trade-offs

- **[Печатные конверсии неполны]** → таблицы `<values>` из `-listx` дают основную массу; остальное закрывается правилами и документируется в `docs/divergences.md`; `-n` — штатный обход.
- **[Порядок тегов у exiftool зависит от внутренней логики]** → план эмиссии на формат строится по наблюдаемому выводу и фиксируется golden-тестами; при расхождении правится план, а не «подгоняется» компаратор.
- **[HEIC/RAW через `nom-exif` может отставать]** → fallback включён по умолчанию; HEIC-файлы с нестандартными box'ами уходят в делегат без падения.
- **[MakerNotes трёх вендоров — это большой объём]** → в MVP только подмножество «съёмочные» теги; остальное — предупреждение и fallback; расширение не трогает CLI и модель.
- **[Память при гигантских XMP-блоках]** → лимит на размер разбираемого блока, при превышении — предупреждение и пропуск блока.
- **[Совместимость с будущими версиями exiftool]** → версия эталона — константа; обновление = новый снимок `-listx`, регенерация таблиц, пересборка golden-корпуса, отдельный PR.
- **[Разные ОС дают разный FilePermissions/FileSize]** → нормализация системных полей в один формат, тесты на Linux; macOS/Windows — после MVP.

## Migration Plan

Greenfield: репозиторий создаётся с нуля, миграции данных нет. Порядок внедрения: скелет workspace → кодогенерация таблиц → JPEG/TIFF-чтение и JSON-писатель → CLI → HEIC/RAW и MakerNotes → fallback → корпус, дифф-тесты и бенчмарки. Откат не требуется: exiftool остаётся эталоном, а `--fallback=always` позволяет использовать etng как обёртку над ним на любом этапе.

## Open Questions

- Публикация в crates.io, лицензия и CI-матрица (Linux/macOS/Windows) — решается после стабилизации API, на архитектуру не влияет.
- Нужны ли `-csv` и `-X` в первой публичной версии — зависит от первых пользователей; добавляется отдельным изменением без правок ядра.
- Поддержка видео/аудио (MOV/MP4) — вероятное следующее изменение; `nom-exif` уже умеет их читать, но модель тегов и план эмиссии для них не спроектированы.
