# Design

## Context

JSON-эмиттер потоковый: записи пишутся по мере обработки чанков, заголовок не нужен. CSV требует знать все колонки до первой строки. Эталонное поведение exiftool (проверено на корпусе):

- при выборе `-Model -Make` заголовок `SourceFile,Model,Make` — порядок аргументов, канонический регистр (`-make` → `Make`);
- без выбора — union по всем файлам, **алфавитно** (165 колонок на Canon_40D + Nikon_D70);
- exiftool обрабатывает все файлы до первой строки (10 с на 2000 файлов), то есть буферизует;
- `-csv -b -ThumbnailImage` → `base64:...`; без `-b` — заглушка в кавычках;
- `-csv -j` — CSV побеждает;
- `-x Model` убирает колонку и поле; `-x` сильнее `-TAG`;
- `-n` даёт машинные значения (`Orientation=1`, `FileSize=7958`).

## Goals / Non-Goals

**Goals:**

- `-csv` с точным составом/порядком колонок и корректным экранированием.
- `-x`/`--exclude` для всех режимов вывода.
- Ограниченная память на больших батчах: не держать все отчёты.
- Совместимость с существующими `-b`, `-n`, `-G`, `-TAG`.

**Non-Goals:**

- `-X` (RDF/XML) — отдельный формат, не входит в это изменение.
- Запись CSV в файл (`-csv=FILE`), `-w`, BOM, выбор разделителя.
- Пропуск парсинга исключённых тегов: фильтр работает на выводе, чтобы не менять композиты.

## Decisions

### D1. Двухпроходный сбор колонок без выбора тегов

Первый проход читает файлы и собирает только ключи колонок в `BTreeSet<String>` (сортировка по алфавиту), отчёты сразу отбрасываются. Второй проход читает файлы заново и пишет строки. Память остаётся O(колонки), а не O(файлы). Цена — двойной парсинг: для 10k JPEG это ~0.5 с против 49 с у exiftool.

При непустом `-TAG` колонки известны заранее (порядок аргументов), поэтому достаточно одного прохода.

### D2. Канонические имена колонок

`ReadOptions.selection` хранится в верхнем регистре для сопоставления. Для заголовка имя разрешается через таблицы тегов: поиск без учёта регистра по `name` (и группе, если указана) возвращает каноническое `Name` и группу. Системные поля маппятся на канонические имена (`FileSize`, `MIMEType`, …). Неизвестное имя остаётся как введено — CLI уже валидирует выбор.

### D3. Порядок и состав колонок

- `SourceFile` всегда первая.
- Выбор: колонки в порядке аргументов, дубликаты схлопываются.
- Без выбора: union ключей (с префиксом `-G`/`-G1`), алфавитная сортировка.
- `-x` применяется до добавления ключа, поэтому исключённые теги не создают колонок.
- Пустая ячейка — если у файла нет тега.

### D4. Значения и экранирование

Значение ячейки повторяет текстовое представление exiftool: print-conversion, при `-n` — машинное; `Value::Bytes` — `base64:<data>` при `-b`, иначе заглушка. CSV-экранирование: ячейка в кавычках, если содержит `,`, `"`, `\n` или `\r`; внутренние кавычки удваиваются. Заголовки экранируются тем же правилом.

### D5. Общий фильтр `wants`

В `ReadOptions` появляется `exclude: Vec<String>` и метод `wants(group0, group1, name) = selects(...) && !excluded(...)`. Его используют JSON-эмиттер, текстовый и raw-писатели, CSV. Композиты по-прежнему вычисляются из всех тегов — как в exiftool, где `-x` влияет только на вывод.

### D6. Приоритет режимов

`-csv` проверяется раньше `-j`: при обоих флагах выводится CSV. `-csv -b` использует тот же base64-кодировщик, что и JSON.

## Risks / Trade-offs

- **[Двойной парсинг без выбора]** → осознанный обмен CPU на память; на корпусе всё равно на порядки быстрее exiftool. При появлении очень больших файлов можно добавить буферизацию отчётов вместо второго прохода.
- **[Fallback вызывается дважды]** → для файлов, требующих делегирования; в первом проходе диагностика подавляется, в втором — обычная.
- **[Канонизация имён]** → поиск по таблицам без учёта регистра; при коллизии групп берётся первое совпадение, как и в текущем выборе.
- **[`-x` не ускоряет парсинг]** → ожидаемо: фильтр на выводе; ускорение пропорционально объёму выводимых полей.

## Migration Plan

Флаги аддитивные; без `-csv`/`-x` поведение не меняется. Откат — revert коммита.
