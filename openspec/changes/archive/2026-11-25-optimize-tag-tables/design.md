# Design

## Context

`etng-tags` встраивает `tags.tsv` (31 942 строки, 4.5 МБ) через `include_str!`. Текущая реализация при первом обращении разбирает **все** строки в `Vec<TagDef>`, строит два `HashMap` (group+name, table+id) и `Vec` печатных конверсий на каждый тег. Это ~30 мс на процесс и определяет время одиночного файла.

Ограничения:

- формат `tags.tsv` и генератор (`cargo xtask generate-tags`) менять не нужно;
- вывод должен остаться побайтово прежним на golden-корпусе;
- `Exif::Main` — таблица, встречающаяся в нескольких group 1 (`IFD0`, `IFD1`, `SubIFD`, `MakerNotes`), поэтому отображение table→group неоднозначно и должно сохранять текущий порядок первого совпадения;
- пакетный режим (rayon) обращается к таблицам конкурентно.

## Goals / Non-Goals

**Goals:**

- Одиночный файл: <10 мс, растяжимо <5 мс (сейчас ~35 мс).
- `-ver` и ошибки использования остаются <1 мс.
- Батч не медленнее текущего; память не растёт с числом файлов.
- Нулевой дифф с golden-корпусом.

**Non-Goals:**

- Смена формата данных, бинарная кодогенерация, разбиение на файлы по группам.
- Изменение публичного API `find_name`/`find_table_id`.
- Оптимизация самих парсеров JPEG/TIFF/HEIC.

## Decisions

### D1. Один дешёвый проход по RAW для индекса

При инициализации таблиц строки не разбираются в `TagDef`: выполняется один проход, который для каждой строки извлекает только group 1 и table (два `split` без аллокаций) и складывает срез строки в `lines_by_group: HashMap<&'static str, Vec<&'static str>>` и `table_groups: HashMap<&'static str, Vec<&'static str>>` (порядок первого появления, дедупликация group). Это ~32k дешёвых операций (~1–2 мс) вместо полного разбора.

### D2. Разбор группы по требованию с кэшем

`Tables::group(g1)` под `Mutex` проверяет кэш; при промахе разбирает только строки этой группы в `GroupData { defs, by_name, by_id }` и удерживает результат через `Box::leak`, чтобы API мог возвращать `&'static TagDef`. Разбор идёт под замком (группы маленькие, конкуренция только на первом обращении), что исключает двойной leak.

### D3. Печатные конверсии — срез строки

`TagDef` хранит `values_raw: &'static str` (поле 8 TSV). `print_value` разбирает пары `id\x1e label` на месте; `Vec` на каждый тег не создаётся. Для тегов без конверсий это пустой срез.

### D4. Неоднозначные таблицы — список групп в порядке появления

`find_table_id(table, id)` перебирает `table_groups[table]` в порядке первого появления и возвращает первый `TagDef` с нужным id. Это сохраняет текущую семантику: для `Exif::Main/513` первым идёт `IFD1` (`ThumbnailOffset`), для `271` — `IFD0` (`Make`).

### D5. CLI-валидация имён без загрузки таблиц

`Tables::has_name(name)` и `has_group_name(group, name)` сканируют сырые строки, сравнивая поля без учёта регистра. Вызываются только при наличии `-TAG`/`-GROUP:TAG`, поэтому обычный запуск их не оплачивает.

### D6. Публичный API не меняется

Сигнатуры `find_name`, `find_table_id`, `find_group_id`, `names_in_group`, `defs` сохраняются. `defs()` теперь возвращает объединение загруженных групп; используется только в тестах/утилитах, поэтому документируется как «загруженные на данный момент».

## Risks / Trade-offs

- **[`Mutex` на первом обращении]** → замок удерживается только при разборе новой группы; после прогрева — чтение из кэша. Батч с 12 потоками грузит ~6 групп один раз.
- **[Память растёт с числом загруженных групп]** → ограничено числом групп в данных (1 224), на практике 5–10; каждая группа — тысячи небольших записей, не файлы.
- **[Семантика `defs()` меняется]** → метод используется только внутри тестов и не входит в контракт CLI; задокументировано.
- **[Расхождение из-за порядка групп]** → покрыто тестами на `Exif::Main/513` и `271` + golden-корпус.

## Migration Plan

Внутренняя переработка без миграции данных. Откат — revert коммита; формат `tags.tsv` не меняется.
