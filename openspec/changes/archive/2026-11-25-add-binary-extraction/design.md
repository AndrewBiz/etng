# Design

## Context

Модель значений (`Value`) уже различает `Bytes(Vec<u8>)` и скаляры. Для EXIF `undefined`-тегов байты сохраняются, но миниатюра и превью CR2 не извлекаются: байты миниатюры вообще не читаются, а `PreviewImage` заполняется нулями нужной длины. JSON-эмиттер печатает `Bytes` заглушкой, текстовый writer — только `print`/`display`.

Эталонное поведение exiftool (проверено на Canon_40D.jpg, exiftool 13.55):

- `-b -Make` → `Canon` без перевода строки; `-b -Orientation` → `1` (без print-conversion);
- `-b -Model -Make` → значения в порядке аргументов, без разделителей;
- `-b` без выбора тегов → все поля подряд, включая системные;
- `-j -b -ThumbnailImage` → `"ThumbnailImage": "base64:/9j/..."`;
- `-j -b -Make` → обычная строка `"Canon"`;
- смещение миниатюры в IFD1 отсчитывается от начала TIFF-заголовка (в JPEG — от начала EXIF payload), длина — `ThumbnailLength`.

## Goals / Non-Goals

**Goals:**

- `-b`/`--binary` в текстовом и JSON-режимах с поведением, совместимым с exiftool.
- Реальные байты `IFD1:ThumbnailImage` (JPEG/TIFF/HEIC) и `IFD0:PreviewImage` (CR2).
- Нулевой регресс обычного (`без -b`) вывода: заглушка для байтов остаётся той же.
- Диагностика только в stderr, коды возврата прежние.

**Non-Goals:**

- Извлечение ICC-профиля и произвольных XMP-пакетов как отдельных тегов.
- `-b` в fallback-режиме (системный exiftool не вызывается ради бинарных данных).
- Потоковая передача очень больших видео-контейнеров; текущий mmap-путь сохраняется.
- `-w`/`-o` и прочие способы раскладки по файлам.

## Decisions

### D1. Бинарность определяется вариантом `Value::Bytes`

Никаких новых флагов у тега: всё, что парсер положил в `Value::Bytes`, считается бинарным. Это совпадает с текущей логикой заглушки и автоматически покрывает `undefined`-теги, миниатюру и превью.

### D2. Сырой текстовый вывод — отдельный writer

В CLI при `binary && !json` не используется `Emitter`: для каждого файла значения пишутся напрямую в `BufWriter`.

- При пустом выборе — системные поля в обычном порядке, затем теги в порядке отчёта.
- При выборе — по одному значению на каждый `-TAG` в порядке аргументов; первое совпадение (системное поле или тег).
- `Value::Bytes` → байты как есть; остальные → `Value::display()` (не `print`), что даёт `1` для `Orientation` и `1/160` для `ExposureTime`.
- Никаких переводов строк и разделителей между значениями и файлами.

### D3. JSON: `base64:`-префикс

`Emitter::tag_value` при `opts.binary` и `Value::Bytes` возвращает `"base64:<standard-base64>"`. Кодировщик пишется локально (алфавит A–Z a–z 0–9 + /, padding `=`), без новой зависимости. Остальные значения и порядок полей не меняются.

### D4. Извлечение миниатюры после разбора EXIF

`ThumbnailOffset`/`ThumbnailLength` уже попадают в теги IFD1. После `exif::parse`:

- JPEG/HEIC: срез EXIF payload по `offset..offset+length`;
- TIFF: срез файла по тем же смещениям (они относительны начала TIFF);
- тег `EXIF/IFD1/ThumbnailImage` вставляется сразу после `ThumbnailLength`, чтобы порядок совпал с exiftool.

Если срез выходит за границы, тег не добавляется (без паники); длина берётся из `ThumbnailLength`.

### D5. CR2: превью из файла, а не нули

`adjust_cr2` получает доступ к данным файла: после переименования `StripOffsets`/`StripByteCounts` в `PreviewImageStart`/`PreviewImageLength` байты берутся из `data[start..start+length]` и вставляются после `PreviewImageLength`. Это убирает фальшивые нули и сохраняет место тега в порядке вывода.

### D6. Fallback не участвует

Если файл требует fallback, в режиме `-b` делегирование не выполняется: выводится ошибка/предупреждение штатным путём. Причина — системный exiftool пришлось бы вызывать с другим контрактом вывода; это отдельная задача.

## Risks / Trade-offs

- **[Большой stdout]** → `-b` без выбора тегов печатает все значения, включая сырые блоки; это поведение эталона, ответственность пользователя.
- **[Порядок выбора]** → exiftool выводит выбранные теги в порядке аргументов; при пустом выборе — в порядке файла. Реализуем оба режима, тесты фиксируют.
- **[Смещения вне границ]** → тег пропускается; предупреждение не добавляется, чтобы не менять коды возврата на повреждённых файлах.
- **[Fallback-ограничение]** → документируется; для поддерживаемых форматов (`JPEG/TIFF/HEIC/CR2/DNG/NEF`) fallback не нужен.

## Migration Plan

Флаг аддитивный; поведение без `-b` не меняется, кроме появления реального `IFD1:ThumbnailImage` (значение-заглушка совпадает с exiftool). Откат — revert коммита.
